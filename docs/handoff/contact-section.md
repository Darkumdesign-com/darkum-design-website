### Contact section troubleshooting round 2, map shadow, address spacing, form card height (2026-08-26)

Three issues raised after the bilingual pass above, one resolved outright, one CSS-confirmed, one left open pending a design decision.

**Map's inset box-shadow not visible at its top corners, resolved 2026-08-26.** Sobhy had already correctly ruled out `.dkd-contact-map-section`'s `z-index: 1` (disabled it, shadow still didn't appear). Actual cause: an inset box-shadow paints as part of the parent element's own box, underneath its children, regardless of z-index, that's basic CSS paint order, not a stacking bug. The Google Maps iframe sat flush against `.dkd-contact-section`'s edges with zero gap (the same reason `overflow: hidden` successfully clips it into rounded corners), so there was no exposed sliver of the parent's own box left for the inset glow to render into at the top, it wasn't hidden behind something, there was structurally nowhere for it to paint. **Sobhy chose the padding option** over leaving the map flush/shadowless: `padding: 10px` added to `.dkd-contact-section`, insetting both the map and the Address/Form row from the outer edge on all sides so the glow has room to show fully around the whole card. Confirmed working live by Sobhy.

**New side effect from that padding fix, unresolved, next session's starting point:** the map itself now shows square corners at its top-left and top-right, since it's no longer flush against the parent's edge. Before the padding, the map's own corners were being clipped into rounded shapes by the parent's `overflow: hidden` + `border-radius: 20px`, since clipping only affects content actually touching the edge. Now that the map sits inset by 10px, it's a separate rectangular block with its own square corners, no longer touching the parent's clipped boundary, so the parent's rounding doesn't reach it anymore. **Likely fix:** give `.dkd-contact-map-section` (or its inner iframe) its own `border-radius` and `overflow: hidden` directly, rather than relying on the parent's. Not yet attempted, confirm the map block's exact selector/structure via DOM inspection first rather than guessing, same caution as the rest of this section's CSS work.

**Address card spacing fixed.** An accidental empty `<p>` block, same category of mistake as the stray "Text (Adv)" block caught before the 2026-08-25 save, this one wasn't caught in time, sat between the Address heading and its paragraph, adding a uniform blank-line gap that made heading/address/heading/hours all read as evenly spaced. Confirmed safe to delete outright rather than mask with a negative margin, since the heading-icon CSS's `h3:first-of-type`/`h3:nth-of-type(2)` selectors only count sibling `<h3>` elements, unaffected by a `<p>` between them. A real `margin-top` on the Store Hours heading was added to `additional-css.css` instead, giving deliberate extra separation before Store Hours specifically rather than uniform spacing throughout, starting value not yet confirmed at live content length.

**Form card over-expanding, root cause confirmed and fixed.** Kadence's Row Layout stretches sibling columns to match whichever is tallest by default. ### Contact section troubleshooting round 3, paragraph margin fix, and a live-CSS-push near miss (2026-08-26)

**Empty `<p>` follow-up:** the "tags came back" mystery after deleting them turned out to be a red herring, Sobhy independently diagnosed via DevTools console that Kadence sets `margin-bottom: var(--global-md-spacing)` (2rem) on every `<p>` by default, which was the real source of the uniform-looking spacing between all four elements, not the deleted empty paragraphs reappearing. Added to `additional-css.css` rescoped to `#dkd-contact-panels-row .dkd-address-card p` instead of the bare class selector, since `kb-palette-10` is a shared Global Palette token other paragraphs elsewhere could carry too. This superseded and replaced the earlier speculative `h3:nth-of-type(2) { margin-top: 1.75em; }` rule, which was confirmed via a live-CSS read to have never actually been pushed live, so it was removed rather than stacked on top of the real fix.

**First attempt at pushing Additional CSS via WP-CLI emptied the live field.** Following Sobhy's go-ahead to push CSS changes directly instead of copy-pasting into the Customizer, the first attempt used `wp post update 83 --post_content="$(cat file)"` over SSH. The CSS file contains double quotes throughout (SVG data URI backgrounds, several `url("...")` values), which broke out of the shell's double-quoted argument the moment the content was interpolated, so WP-CLI received and wrote an empty value, reporting "Success" despite writing nothing. **Live Additional CSS was briefly completely empty as a result**, caught immediately via a follow-up `LENGTH(post_content)` check rather than assumed correct from the command's own success message. **Fixed by avoiding shell interpolation entirely**: a small PHP file uploaded via SFTP alongside the CSS, executed with `wp eval-file`, reading the CSS via `file_get_contents()` and writing it with `wp_update_post()` directly, no shell quoting involved at any point. Confirmed restored and correct via `LOCATE()` SQL checks on known unique strings at expected byte offsets, not just a byte-count match. **This `eval-file` + `file_get_contents` pattern is now the standing method for any future live CSS push**, the `--post_content="$(cat file)"` approach is not to be used again for content containing quotes. See `wp-cli-workflow-and-tooling.md` for the standalone writeup of this method.

Also worth noting for future diagnosis: `Invoke-SSHCommand` output piped through `grep`/`wc`/`tail` on large multi-KB content proved unreliable during this session, returning empty results on genuinely non-empty data more than once, while compact single-value SQL queries (`SELECT LENGTH(...)`, `SELECT LOCATE(...)`) were consistently reliable. Prefer the latter for verifying live database state through this tool going forward, and don't treat an empty piped-text result alone as proof of a problem without a compact-query cross-check first.

### Contact section troubleshooting round 4, the nested `<p>` bug, session wrap (2026-08-26)

**The "deleted empty `<p>` tags keep coming back" mystery, actually solved.** Sobhy pushed back hard, and correctly, on the cache explanation offered for this: he'd already ruled out caching by flushing GoDaddy's cache after every change and cross-checking in a second browser. The real cause, visible directly in a Code Editor screenshot: both bilingual paragraphs (Address and Store Hours) had a genuinely malformed **nested `<p>` tag** in their raw HTML, an orphaned copy of the *original* pre-rewrite paragraph's opening tag (still carrying its old `column-count` styling) wrapping the *new* `dkd-bilingual-pair` paragraph, with an extra unmatched closing `</p>` at the end:
```html
<p class="..." style="column-count:2"><p class="... dkd-bilingual-pair" style="display:flex;...">
  <span lang="en" dir="ltr">...</span><span lang="ar" dir="rtl">...</span>
</p></p>
```
`<p>` tags can't legally nest per the HTML5 spec, so browsers auto-close the outer one the instant they hit the inner opening tag, which is exactly what rendered as a phantom "empty paragraph" sitting before the real content, not a caching artifact and not something Sobhy imagined or mis-clicked. It also explains why the earlier `margin: 0` CSS fix (round 3) still visibly worked: `#dkd-contact-panels-row .dkd-address-card p` matches any `<p>` in that card, so it caught the real content regardless of the orphaned wrapper sitting next to it, masking the markup problem rather than the markup actually being clean. Best guess at the cause: editing the block's Code Editor by replacing only the text *between* the original tags rather than deleting the whole original opening/closing pair, easy to do when the single-block code view only shows that block's content, not its outer tag boundaries, exactly the kind of edit that's fragile to do by hand.

**Fixed via the established safe-push method, not by hand-editing in the block editor again.** Since both blocks are genuine `<!-- wp:html -->` Custom HTML blocks (from the earlier "Convert to HTML" step), there's no Gutenberg block-attribute structure to break, just raw text. Current `post_content` for post 35 pulled fresh via WP-CLI, the two known-exact broken opening-tag strings and the two `</p></p>` closers removed via precise local string substitution (verified: content length dropped by exactly the removed characters, `column-count` and `</p></p>` both confirmed absent afterward, `dkd-bilingual-pair` count unchanged at 2), then pushed live via the `eval-file` + `file_get_contents` method. Confirmed clean at the database level via `LOCATE()`/`LENGTH()` SQL checks, not just a success message. **Confirmed by Sobhy in the actual block editor afterward: both phantom empty paragraphs are genuinely gone**, not just visually suppressed.

**Standing capability established this session, applies to any future work, not just the Contact section:** direct, safe live pushes to WordPress are now available for both Additional CSS (`custom_css` post ID **83**) and page content (Home page post ID **35**), via Posh-SSH (`Install-Module -Name Posh-SSH -Scope CurrentUser`, already installed) plus the `eval-file` + `file_get_contents()` pattern, never raw shell interpolation like `--post_content="$(cat file)"`, which silently emptied the CSS field once already this session when the content contained quote characters. Verify every push with a compact SQL query (`LENGTH`, `LOCATE`) against known content, not by trusting the command's own "Success" message and not via large piped-text reads, which proved unreliable through this tool. Native Gutenberg block content (regular Paragraph/Heading/Column blocks, not Custom HTML) still goes through the visual editor or per-block Code Editor by hand, not raw pushes, since that content is validated/reconciled by Gutenberg's own parser in a way raw writes bypass entirely, a real, different risk from pushing to a Custom HTML block or the CSS field. See `wp-cli-workflow-and-tooling.md` for the standalone writeup of the `eval-file` push method itself.
