# Homepage, Header, and Footer

### Homepage build, started 2026-08-17

**Approach: blank page, not a template.** Every Kadence homepage template assumes single-language, single-column content flow, the site's core requirement (simultaneous EN/AR, side-by-side, no switcher) conflicts with that structure more than it benefits from any pre-filled placeholder content. Decision: build the page blank, but pull individual **Patterns** (not full Page templates) into sections that don't need bilingual dual-column treatment (e.g. footer, simple dividers) as a time-saver, hand-build the sections that do need it (hero, most content blocks).

**Header/footer:** Kadence theme's free-tier Customizer-based header/footer builder (Appearance → Customize → Header/Footer) covers this natively, no separate template plugin needed. Applies sitewide by default; conditional/multiple headers is a Kadence Pro feature, not needed for this single-header one-page site.

**Hero ticker, ported from the coming-soon page into a Kadence Custom HTML block (2026-08-17):** the confirmed scope (`domain-and-scope-decisions.md`, 2026-08-13) calls for a smoother/more polished version of the coming-soon page's existing ticker, not a rebuild, same crossfade logic, EN-slides-right/AR-slides-left direction, dot nav, arrow buttons, pause-on-hover/focus, `aria-live` announcer, `prefers-reduced-motion` handling. ### Hero ticker polish pass (2026-08-26)

All six items from a brainstormed "polish this" list built in one session: touch swipe navigation on mobile, a direction-aware slide+fade transition (matching the standing EN-from-right/AR-from-left design intent, previously only a flat crossfade), keyboard Left/Right navigation while the nav row has focus, an autoplay progress bar under the dots that visually counts down each 7-second cycle and pauses in sync with the existing hover/focus pause behavior, larger invisible tap targets on the dots (24x24px hit area wrapping the same visible 7px dot, closer to WCAG's touch-target guidance than the literal 7px hit area before), and a softer fade-in on first page load instead of an instant opacity snap.

**A real bug was caught mid-build, not shipped.** The first version sequenced the entrance animation with a double `requestAnimationFrame` call (a standard technique for forcing a browser to paint an initial state before animating away from it). Confirmed live via `document.hidden`/`document.hasFocus()` checks that this genuinely never fires when a tab is backgrounded, Chrome fully suspends `requestAnimationFrame` callbacks for hidden tabs, it isn't merely throttled. That meant the hero text would never appear at all for anyone whose tab happened to load in the background (a new tab opened in the background, certain mobile/prerender scenarios), not a hypothetical edge case, reproduced directly. **Fixed by switching to a short `setTimeout` instead** (20ms), which does fire in a backgrounded tab, confirmed by directly reading the element's inline `style.opacity`/`style.transform` values (not just `getComputedStyle`, which can lag behind in a tab that isn't actively painting) and finding them correctly set on schedule.

**Testing note for future sessions:** this project's browser automation tab reports `document.hidden = true` for every tab it controls, including freshly created ones and after attempting to bring the browser window to OS-level focus, and does not appear to paint/render frames while in that state (confirmed via screenshot showing no ticker text despite correct underlying DOM/style state). This makes visual/animation-smoothness verification through this specific tool unreliable, functional verification (does clicking next/prev or pressing arrow keys correctly advance the slide, wrap around, update the dots and `aria-live` status) still works fine and was used instead, confirmed via direct `.click()` calls and dispatched `KeyboardEvent`s with proper waits for the (intentionally delayed, matching the fade transition) `updateDots`/`updateStatus` calls. A real visual spot-check in an actual foregrounded browser tab is still worth doing to judge the animation's actual feel, that part genuinely couldn't be confirmed through this tooling.

Pushed live via `wp-custom-edits/Scripts/wp-push.ps1` against post 35, verified via exact byte-length match each time (`eval-file`'s reported new length matched the SQL `LENGTH()` verification exactly on both the initial build and the `requestAnimationFrame`→`setTimeout` fix).

**Key lesson learned building this (2026-08-17): a Kadence Custom HTML block only accepts one self-contained blob**, separate `.html`/`.css`/`.js` files (or `<link rel="stylesheet">`/`<script src="...">` referencing them) don't work, since those files aren't hosted anywhere on the live site. CSS must be inlined in a `<style>` tag and JS in a `<script>` tag, all pasted together as one block. First attempt only showed the arrow icons (default Kadence button styling) with no ticker text or dots, because without the JS running, the text nodes stay empty and dots never generate, worth remembering for any future Custom HTML block on this site. Also caught mid-fix: a typo in the CSS (`'Source San 3'` missing the "s", should be `'Source Sans 3'`), and a missing `.sr-only` class definition (used by the screen-reader status announcer but only previously defined in the coming-soon page's own `css/style.css`, not carried over into the WordPress block).

**Background color troubleshooting (2026-08-17):** after adding the ticker, an unwanted brown background (`#996633`, brand primary color) surrounded it despite the Row Layout and both nested Section blocks showing no background color set at the block level. Root cause: **Kadence's page-level "Content Background" setting** (Customizer → [Page] → Default Page Layout → Content Background, distinct from the sitewide Site Background) was overriding at the page level, invisible from any individual block's own Style panel. ### About/Story section, structure built 2026-08-26, content still placeholder

**Built as its own separate Row Layout, `dkd-about-row`** (both HTML anchor and Additional CSS class set to the same value), sitting right after the hero section. Three Sections inside the row: a full-width Heading on top ("Our Story / قصتنا", wood-light `#bd9c7a`, centered, matching the Contact section's heading treatment), a real Advanced Image block on the left (`about-section-img_1448x1086px.png`, one of the ChatGPT-generated renders Bido and Noura already approved, not a placeholder), and a self-contained Custom HTML block on the right holding the bilingual paragraph grid.

**CSS Grid auto-placement, no manual `grid-column`/`grid-row` on any element, deliberately simpler than the coming-soon page's tagline/coming-soon pairing fix.** The Custom HTML block is one self-contained blob (style tag + markup together, same convention established for the hero ticker, since a Kadence Custom HTML block only accepts one blob and can't reference external files). Six `<p>` tags in strict source order (EN1, AR1, EN2, AR2, EN3, AR3). Mobile-first base CSS is a single-column grid, so with no grid override the six paragraphs just stack in that source order, already correctly paired without any special mobile-only rule. A `min-width: 620px` media query (same breakpoint as the coming-soon page's own bilingual grid) switches to a 2-column grid; because no paragraph has explicit placement, the browser's default auto-placement (left to right, top to bottom, one row at a time) naturally lands EN1/AR1 on row 1, EN2/AR2 on row 2, EN3/AR3 on row 3. This differs from the coming-soon page's tagline/coming-soon pair, which needed explicit `grid-column`/`grid-row` values on each element since it wasn't relying on auto-placement; here, adding a future 4th paragraph pair means adding two more `<p>` tags in order, no CSS to touch.

**Arabic paragraph styling matches the established Cairo-weight lesson:** `.dkd-ar` sets `font-family: 'Cairo', sans-serif`, `font-weight: 400`, and `letter-spacing: 0`, same reasoning as the ticker and the coming-soon tagline fix elsewhere in this file, Cairo reads visually heavier than Source Sans 3 at the same numeric weight, and Latin letter-spacing conventions don't apply to Arabic's connected letterforms.

**Verified live at both breakpoints via screenshot**, not just assumed from the CSS: desktop shows three correctly-paired EN/AR rows beside the image; resizing to a mobile viewport (both the wp-admin editor's device preview and an actual narrow browser window) confirmed the six paragraphs collapse to one column and stack in the exact EN1/AR1/EN2/AR2/EN3/AR3 order, not grouped by language.

**Content is bracketed English/Arabic placeholder text** (three pairs, e.g. "[EN placeholder, paragraph 1 of the About/Story section, real copy pending Dema.]"), deliberately generic rather than drafted-sounding, so nobody mistakes it for actual copy. Real content is blocked on Dema (see `business-context.md`), swapping it in is a straight edit inside the same Custom HTML block, no rebuild needed. ### Footer redesign (2026-08-19/20/21), desktop confirmed live, mobile partially addressed

**Supersedes the earlier "5-per-row grid + copyright color" fix** (originally drafted 2026-08-18, flagged as "not yet confirmed live" in `resolved-items-log.md`), that fix did ship, and this section covers the fuller redesign that grew out of it once Sobhy started using the footer in the browser.

**Flex-direction fix, the root enabler for everything else:** the footer's three columns (About, Follow us/social icons, Menu) live inside `.site-footer-section`, which defaults to `flex-direction: row`. Adding an H3 heading above each column as a sibling caused it to render as an extra row-item instead of stacking above the column's existing content. Fixed via Additional CSS: `.site-footer-section { flex-direction: column; }`, confirmed working via Claude in Chrome inspection before being applied. The footer navigation menu (Menu column) needed the same treatment separately, since it's nested inside its own nav/ul structure: `.footer-navigation .menu { flex-direction: column; }`. Once switched to columns, the nav items' link padding also needed zeroing, since they'd been relying on padding alone (not margin/gap) for row-spacing, which collapsed the list into a single line with no vertical space once the direction changed.

**H3 headings added above each column, and alignment unified:** "About" kept, "Follow us" added above the social icons, "Menu" added above the footer nav. All three columns' content (including the nav list, which needed the padding fix above) aligned left/start, replacing the previous mixed left/center alignment that was the main source of the footer looking unbalanced. Heading style: wood-light color (`#bd9c7a`) instead of full cream, uppercase, letter-spaced, so headings read as section labels distinct from body content.

**Footer nav link colors and current-page state:** nav links set to cream by default, brand wood (`#996633`) on hover. **Active/current-page indicator done via the `.current-menu-item` class, not `:active`**, CSS `:active` only applies for the literal moment of a mouse press (mousedown to mouseup) and reverts on release, so an underline rule on `a:active` only ever renders during a click, never persistently, which is why it only appeared to work in DevTools with "Force element state" checked. Correct approach, using the class Kadence already applies to the current page's nav item, targets `li.current-menu-item > a` and sets `text-decoration: underline`, alongside the existing color rule Kadence generates natively for the same selector. Confirmed live, Home correctly shows underlined while on the homepage.

**Vertical gradient dividers between columns:** a plain solid border renders as a flat, constant-weight line top to bottom, not achievable with CSS borders alone. Built instead as a pseudo-element with a gradient background, transparent at top and bottom, full color at the vertical midpoint, giving a tapered/artistic look rather than a hard-edged line. Color bumped from brand wood `#996633` to the lighter `#bd9c7a` and width from 1px to 2px for better visibility against the near-black footer background, confirmed sufficient by Sobhy without needing to also narrow the transparent fade.

**Debugging note worth remembering for future Additional CSS work:** the divider rendered completely invisible on the first attempt despite the positioning rules both showing as applied in DevTools' Styles panel. Root cause: the Kadence Additional CSS field's editor (CodeMirror) auto-pairs quote characters as you type, so an empty-string `content` value typed with double quotes normally can silently double up into four quote characters, which is invalid and causes the parser to drop the rest of the declaration block. Fixed by retyping with single quotes, which sidesteps the auto-pairing behavior. Confirmed via DevTools: the pseudo-element either doesn't appear in the Elements tree at all (parse failure, this cause) or appears but renders invisible (a real positioning/sizing/z-index issue, a different cause), useful diagnostic split for next time.

**Column spacing ("footer isn't stretched to page width"), root cause found and resolved natively, 2026-08-21, no CSS needed.** Sobhy reported the three columns weren't filling the boxed 1290px container edge-to-edge, and that applying `justify-content`/`justify-items: space-between` directly hadn't visibly done anything. Root cause: the columns are `minmax(0, 1fr)` grid tracks that already consume 100% of the container width with no leftover space, so `justify-content`/`justify-items` had nothing to redistribute, the properties weren't broken, they just had no effect to have. Confirmed live via screenshot, all three columns now fill the row evenly with both gradient dividers landing correctly.

**Column order swapped (Menu / Follow Us, from the original About / Follow Us / Menu), 2026-08-21, also native, not CSS.** Done by reordering the widgets directly in the Kadence Footer Middle Row Customizer, not via a CSS `order` property. The divider selectors (`.site-footer-middle-section-1`/`-2`) target columns by structural position, not by which widget occupies them, so they continue to land correctly between columns regardless of this reorder, confirmed no divider/heading regression after the swap.

### Arabic font fallback, Explore button contrast, and site title typo (2026-08-21)

**Arabic characters with no `lang="ar"` wrapper were rendering in the wrong font.** Raised via the footer copyright line, whose `{site-title}` dynamic tag outputs "Darkum Design - داركم ديزاين" as one unmarked bilingual string with no element boundary around just the Arabic portion, so the existing scoped `[lang="ar"]` CSS approach couldn't target it. **Root cause confirmed from the theme's actual generated CSS, not guessed:** the body font, `'Source Sans 3'`, has zero Arabic glyph coverage (confirmed against its real Google Fonts `@font-face` subsets, latin/latin-ext/cyrillic/greek/vietnamese only, no Arabic), so unmarked Arabic characters were falling through past it straight to the browser's generic `sans-serif` system font, a different font than the site's intended Cairo.

**Fix: redefine the CSS variable Kadence's own font-family rule already reads from**, rather than editing markup or duplicating scoped rules:
```css
:root {
  --global-body-font-family: 'Source Sans 3', 'Cairo', sans-serif;
}
```
This works because of how CSS font-stack fallback actually resolves: per character, not per element, a browser checks each font in the list in order and uses the first one that has a glyph for that specific character. Cairo has to sit **before** the trailing `sans-serif`, not after, appending it after would never be reached, since the generic keyword already resolves to a real system font with some Arabic coverage of its own, satisfying the fallback before the list ever reaches Cairo. This is CSS-only and not achievable through the Kadence Customizer Typography UI at all, which only supports picking one font per element, not a fallback chain. Confirmed live by Sobhy testing `getComputedStyle` on the ticker's Arabic element directly in the browser console, resolves to Cairo.

**Made one existing rule redundant, removed:** `.site-info .footer-html-inner p [lang="ar"]{ font-family: 'Cairo', sans-serif; }` (the original scoped fix for the footer copyright's separate, properly-marked Arabic sentence) was removed 2026-08-21 once the global fallback confirmed working, Sobhy verified no visual regression.

**Scope note, not yet needed but worth remembering:** this fix covers body text (paragraphs, inputs, and, via normal inheritance, h5/h6). Headings h1–h4 are hardcoded directly to `font-family: Alice, serif;` in Kadence's own CSS (not through a variable), so they're immune to this fix. Nothing on the site currently puts Arabic inside an actual heading tag, so this hasn't needed addressing, but if it ever does, it will need its own explicit rule.

**Hero ticker's own explicit Cairo/Source Sans 3 declarations deliberately kept, not simplified away.** Considered removing `.ticker-en`/`.ticker-ar`'s own `font-family` lines now that the global fallback makes them technically redundant, but decided against it: `.ticker-ar` pairs a specific `font-weight: 400` and a smaller `clamp()` font-size range against Cairo specifically (documented elsewhere in this file as the fix for Cairo reading visually heavier than Latin type at the same numeric size). Removing the explicit font-family would make that tuning silently dependent on the sitewide default never changing, and the ticker block is otherwise deliberately self-contained. Kept as intentional redundancy.

**Explore button contrast fixed.** The hero's "Explore" button had genuinely low contrast against the rotating background photos (gold-toned fill and text against warm-toned imagery). A `ticker-button` class was added via the Buttons block's own "Additional CSS Class(es)" field (Edit Page > block > Advanced), deliberately not touching the theme's shared button styling used elsewhere on the site. First attempt (a subtle gold `box-shadow`) was flagged as likely to be invisible against the same warm-toned photos causing the original problem, same hue family as the background, so no real contrast. Replaced with a dark shadow using `#2b2620` (the site's own dark brown palette token, `--global-palette5`) for genuine luminance contrast against any of the rotating photos, not just one:
```css
.ticker-button a {
  box-shadow: 0 4px 14px rgba(43, 38, 32, 0.45);
}
```
Confirmed sufficient by Sobhy against the live rotating hero images.
