# WP-CLI Workflow and Tooling

### Safe live-push method: `wp-push.ps1` + `wp-eval-push.php` (generalized 2026-08-26)

Standing, reusable project-wide tooling for pushing content directly to the live WordPress database via WP-CLI over SSH, used for both Additional CSS (`custom_css` post ID **83**) and homepage content (Home page post ID **35**), or any future `post_content` push. Lives at `wp-custom-edits/Scripts/`, see `Scripts/README.md` for full usage and design notes. The full story of how the underlying method was discovered, including the near-miss that briefly emptied the live Additional CSS field, is documented in `contact-section.md`'s "troubleshooting round 3" and "round 4" write-ups, this section is the standalone reference for the method itself.

**The problem with shell interpolation:** an early attempt used `wp post update 83 --post_content="$(cat file)"` over SSH. CSS/HTML content containing double quotes (SVG data URI backgrounds, `url("...")` values, HTML attributes) breaks out of the shell's double-quoted argument the moment the content is interpolated, so WP-CLI can receive and write an empty value while still reporting "Success." This silently emptied the live Additional CSS field once. **Do not use `--post_content="$(cat file)"` for any content containing quotes.**

**The fix:** `wp-eval-push.php`, a small PHP file uploaded via SFTP alongside the target content file, executed with `wp eval-file`, reading the file's contents via `file_get_contents()` and writing them with `wp_update_post()` directly, no shell quoting involved at any point. `wp-push.ps1` is the PowerShell driver that automates the whole round trip: connect, upload, run, verify, clean up.

**Always verify with a compact SQL query, not the command's own success message:** `LENGTH(post_content)` and `LOCATE('known string', post_content)` checks against the database reliably confirm what was actually written. `wp-push.ps1`'s `-VerifyString` parameter automates this. Large piped-text reads (`Invoke-SSHCommand` output piped through `grep`/`wc`/`tail`) proved unreliable on multi-KB content during this project, returning empty results on genuinely non-empty data more than once, prefer compact single-value SQL queries for verifying live database state through this tool.

**Scope note:** native Gutenberg block content (regular Paragraph/Heading/Column blocks, not Custom HTML) still goes through the visual editor or per-block Code Editor by hand, not raw pushes, since that content is validated/reconciled by Gutenberg's own parser in a way raw writes bypass entirely, a real, different risk from pushing to a Custom HTML block or the CSS field.

### Lessons learned generalizing this tooling (2026-08-26)

The first working version of this method (built the same day, during the Contact section's map-corner fix) was a one-off pair of scripts written to `$env:TEMP`, per the general "write scripts to Temp for Desktop Commander" habit. That habit doesn't fit reusable tooling: Temp has no version history and gets silently lost between sessions. Corrected: reusable automation belongs in the repo (`wp-custom-edits/Scripts/` for WordPress-push tooling specifically), Temp stays reserved for genuinely one-off diagnostic scripts, and specifically for working around Desktop Commander's inline-shell-variable limitation, not as a general script home.

Three real gotchas surfaced while generalizing and testing the tooling, worth recording so they aren't rediscovered the hard way next time:

- **`pwsh` vs `powershell.exe`.** Posh-SSH was installed under PowerShell 7's CurrentUser module scope (`Documents\PowerShell\Modules`). The legacy Windows PowerShell 5.1 (`powershell.exe`, the bare `powershell` alias) reads modules from a completely different path (`Documents\WindowsPowerShell\Modules`) and can't see it at all, every Posh-SSH cmdlet fails with "term not recognized." Any script using Posh-SSH must be invoked with `pwsh -NoProfile -File`, never the plain `powershell` alias.
- **`Set-SFTPItem` doesn't rename on upload.** It always keeps the source file's own basename; passing a full target file path (a name that doesn't already exist) as `-Destination` fails outright, since it's trying to write into that exact path as if it were a directory. Upload to a destination *directory* instead, then reference the file by its own original name in whatever runs next. An earlier version of this tooling didn't know this and referenced the wrong filename in its `wp eval-file` call as a result, though it failed loudly (`file_get_contents()` returning false, an early return with a nonzero exit code) rather than silently.
- **This SFTP account is not chrooted.** `Get-SFTPLocation` returns the real absolute home directory (`/home/<user>`), and a path with a leading slash (`/wp-push-tmp/`) means the true filesystem root, not the SFTP home, confirmed via `Test-SFTPPath` returning `False` for the leading-slash form and `True` for the same path without one. Paths relative to the session's starting location (no leading slash) are what's needed for anything under the home directory.

The combination of the second and third points above is also why the very first version of this tooling (before generalization) briefly left a stray `additional-css.css` sitting directly in the public web root (`~/html`), a leading-slash destination path that happened to coincidentally resolve to a real top-level `/html` folder, plus filename-preservation-on-upload landing it under the original name instead of the intended scratch name. Caught and cleaned up before it mattered, but it's exactly the class of mistake the current design (private `~/wp-push-tmp` staging directory, `--path` flag so `wp eval-file` never needs `~/html` as its working directory, an explicit `ls` confirmation step before running anything) is meant to make structurally harder to repeat.

### Homepage content mirror + Posh-SSH snapshot tooling (2026-08-26)

After Sobhy raised concern about having no real undo for WordPress content edits, WordPress's own native Revisions are a separate mechanism from Gutenberg's in-editor Ctrl+Z (which is session-only and clears on reload), and it's not yet confirmed whether Revisions are functioning as expected on this GoDaddy setup, a new mirror file was added: `wp-custom-edits\HTML\homepage-content-snapshot.html`, the literal `post_content` field for the Home page. Confirmed **post ID 35**, matching the `35_...` prefix already visible in every Kadence block uniqueID on this page (`wp post list` also surfaced two additional Polylang-generated Home-titled pages, ID 229 "Home - English" and ID 231 "Home - العربية", both `publish` status, Sobhy confirmed these are expected Polylang language variants but hasn't decided whether to unpublish, archive, or delete them, deferred until after the current Contact section work, see `TO-DO-List.md`).

Single continuously-overwritten file, same pattern as `additional-css.css`, git log is the version history, not multiple dated copies. To restore a previous state: open the file at the wanted git revision, copy everything below its header comment, paste into the Home page's Gutenberg Code Editor (Options menu, top right, "Code editor"), replacing the existing content, then Update.

**Pulled via WP-CLI over SSH, not manual copy-paste**, for reliability (`wp post get 35 --field=post_content`). Windows' built-in OpenSSH client can't do password-only auth non-interactively (this host is password-auth only, no key upload support, per the `.env` file's own comment already documenting this), and `plink` wasn't found on PATH, so the **Posh-SSH PowerShell module** was installed instead (`Install-Module -Name Posh-SSH -Scope CurrentUser`, no admin rights needed), which supports scripted password auth via a `PSCredential` built from the password stored in `.env`. Confirmed working 2026-08-26, first pull succeeded, 307-line snapshot saved.

**Habit going forward:** re-pull and overwrite this file after any meaningful homepage change, then commit. Deliberately not added to `TO-DO-List.md` as a recurring checklist item, per Sobhy's direction, this is a standing workflow habit, not a one-off task.
