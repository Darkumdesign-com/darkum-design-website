### Arabic font fallback, Explore button contrast, and site title typo (2026-08-21)

**Arabic characters with no `lang="ar"` wrapper were rendering in the wrong font.** Raised via the footer copyright line, whose `{site-title}` dynamic tag outputs "Darkum Design - داركم ديزاين" as one unmarked bilingual string with no element boundary around just the Arabic portion, so the existing scoped `[lang="ar"]` CSS approach couldn't target it. **Root cause confirmed from the theme's actual generated CSS, not guessed:** the body font, `'Source Sans 3'`, has zero Arabic glyph coverage (confirmed against its real Google Fonts `@font-face` subsets — latin/latin-ext/cyrillic/greek/vietnamese only, no Arabic), so unmarked Arabic characters were falling through past it straight to the browser's generic `sans-serif` system font, a different font than the site's intended Cairo.

**Fix: redefine the CSS variable Kadence's own font-family rule already reads from**, rather than editing markup or duplicating scoped rules:
```css
:root {
  --global-body-font-family: 'Source Sans 3', 'Cairo', sans-serif;
}
```
This works because of how CSS font-stack fallback actually resolves: per character, not per element — a browser checks each font in the list in order and uses the first one that has a glyph for that specific character. Cairo has to sit **before** the trailing `sans-serif`, not after — appending it after would never be reached, since the generic keyword already resolves to a real system font with some Arabic coverage of its own, satisfying the fallback before the list ever reaches Cairo. This is CSS-only and not achievable through the Kadence Customizer Typography UI at all, which only supports picking one font per element, not a fallback chain. Confirmed live by Sobhy testing `getComputedStyle` on the ticker's Arabic element directly in the browser console — resolves to Cairo.

**Made one existing rule redundant, removed:** `.site-info .footer-html-inner p [lang="ar"]{ font-family: 'Cairo', sans-serif; }` (the original scoped fix for the footer copyright's separate, properly-marked Arabic sentence) was removed 2026-08-21 once the global fallback confirmed working — Sobhy verified no visual regression.

**Scope note, not yet needed but worth remembering:** this fix covers body text (paragraphs, inputs, and — via normal inheritance — h5/h6). Headings h1–h4 are hardcoded directly to `font-family: Alice, serif;` in Kadence's own CSS (not through a variable), so they're immune to this fix. Nothing on the site currently puts Arabic inside an actual heading tag, so this hasn't needed addressing, but if it ever does, it will need its own explicit rule.

**Hero ticker's own explicit Cairo/Source Sans 3 declarations deliberately kept, not simplified away.** Considered removing `.ticker-en`/`.ticker-ar`'s own `font-family` lines now that the global fallback makes them technically redundant, but decided against it: `.ticker-ar` pairs a specific `font-weight: 400` and a smaller `clamp()` font-size range against Cairo specifically (documented elsewhere in this file as the fix for Cairo reading visually heavier than Latin type at the same numeric size). Removing the explicit font-family would make that tuning silently dependent on the sitewide default never changing, and the ticker block is otherwise deliberately self-contained. Kept as intentional redundancy.

### Contact section troubleshooting round 4 — the nested `<p>` bug, session wrap (2026-08-26)

**The "deleted empty `<p>` tags keep coming back" mystery, actually solved.** Sobhy pushed back hard, and correctly, on the cache explanation offered for this: he'd already ruled out caching by flushing GoDaddy's cache after every change and cross-checking in a second browser. The real cause, visible directly in a Code Editor screenshot: both bilingual paragraphs (Address and Store Hours) had a genuinely malformed **nested `<p>` tag** in their raw HTML, an orphaned copy of the *original* pre-rewrite paragraph's opening tag (still carrying its old `column-count` styling) wrapping the *new* `dkd-bilingual-pair` paragraph, with an extra unmatched closing `</p>` at the end:
```html
<p class="..." style="column-count:2"><p class="... dkd-bilingual-pair" style="display:flex;...">
  <span lang="en" dir="ltr">...</span><span lang="ar" dir="rtl">...</span>
</p></p>
```
`<p>` tags can't legally nest per the HTML5 spec, so browsers auto-close the outer one the instant they hit the inner opening tag, which is exactly what rendered as a phantom "empty paragraph" sitting before the real content, not a caching artifact and not something Sobhy imagined or mis-clicked. It also explains why the earlier `margin: 0` CSS fix (round 3) still visibly worked: `#dkd-contact-panels-row .dkd-address-card p` matches any `<p>` in that card, so it caught the real content regardless of the orphaned wrapper sitting next to it, masking the markup problem rather than the markup actually being clean. Best guess at the cause: editing the block's Code Editor by replacing only the text *between* the original tags rather than deleting the whole original opening/closing pair, easy to do when the single-block code view only shows that block's content, not its outer tag boundaries, exactly the kind of edit that's fragile to do by hand.

**Fixed via the established safe-push method, not by hand-editing in the block editor again.** Since both blocks are genuine `<!-- wp:html -->` Custom HTML blocks (from the earlier "Convert to HTML" step), there's no Gutenberg block-attribute structure to break, just raw text. Current `post_content` for post 35 pulled fresh via WP-CLI, the two known-exact broken opening-tag strings and the two `</p></p>` closers removed via precise local string substitution (verified: content length dropped by exactly the removed characters, `column-count` and `</p></p>` both confirmed absent afterward, `dkd-bilingual-pair` count unchanged at 2), then pushed live via the `eval-file` + `file_get_contents` method. Confirmed clean at the database level via `LOCATE()`/`LENGTH()` SQL checks, not just a success message. **Confirmed by Sobhy in the actual block editor afterward: both phantom empty paragraphs are genuinely gone**, not just visually suppressed.

**Standing capability established this session, applies to any future work, not just the Contact section:** direct, safe live pushes to WordPress are now available for both Additional CSS (`custom_css` post ID **83**) and page content (Home page post ID **35**), via Posh-SSH (`Install-Module -Name Posh-SSH -Scope CurrentUser`, already installed) plus the `eval-file` + `file_get_contents()` pattern, never raw shell interpolation like `--post_content="$(cat file)"`, which silently emptied the CSS field once already this session when the content contained quote characters. Verify every push with a compact SQL query (`LENGTH`, `LOCATE`) against known content, not by trusting the command's own "Success" message and not via large piped-text reads, which proved unreliable through this tool. Native Gutenberg block content (regular Paragraph/Heading/Column blocks, not Custom HTML) still goes through the visual editor or per-block Code Editor by hand, not raw pushes, since that content is validated/reconciled by Gutenberg's own parser in a way raw writes bypass entirely, a real, different risk from pushing to a Custom HTML block or the CSS field.
