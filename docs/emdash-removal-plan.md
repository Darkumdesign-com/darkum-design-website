## Step 3: Fix each one, minimally

Default replacement is a comma, per the standing rule's own wording ("Use commas or hyphens instead"). For each occurrence:

- If a comma reads naturally in place of the em dash, use a comma.
- If the em dash was doing double duty as a parenthetical aside and a comma would create an awkward run of commas in the same sentence, a plain hyphen, a period splitting it into two sentences, or a small connecting word (", which," ", since," etc.) are all fine, use whichever keeps the sentence grammatical and closest to the original meaning.
- This is not an opportunity to rewrite, re-interpret, or improve the surrounding content. Change only what's needed to remove the em dash and keep the sentence correct.
- Do not touch any Arabic-script content differently from English, the rule applies to both, though Arabic text in this project is unlikely to contain em dashes in the first place.

## Step 4: Special handling for files that mirror or feed live/deployed content

A few files on the list aren't just internal documentation, they're the source of truth for content that's actually live on a website. Fix the em dashes in these the same way as everywhere else, but flag each one distinctly in your Step 5 summary, since fixing them here doesn't automatically update the live version:

- **`wp-custom-edits\CSS\additional-css.css`** is the canonical mirror of what's pasted into WordPress's Customizer → Additional CSS field. Any em dash here is almost certainly inside a CSS comment, not affecting rendering, but if this file changes, it now differs from what's actually live on the WordPress site until someone re-pushes it (the established `eval-file` + `file_get_contents()` method, see `docs/handoff/wp-cli-workflow-and-tooling.md`). Note in your summary whether re-pushing this file live is something Sobhy should do as a follow-up.
- **`wp-custom-edits\HTML\light-catchphrase-ticker.html`** and **`wp-custom-edits\CSS\light-catchphrase-ticker.css`** are the source files for the homepage hero ticker's Custom HTML block content, actually live on the WordPress build. Check carefully whether any em dash here is inside a **displayed catchphrase string** versus a code comment, an em dash in a catchphrase is user-facing typography on the live site, not just internal notes. Flag this distinction explicitly.
- **`js\script.js`** and **`css\style.css`** are the actual deployed source for the coming-soon page at `darkumdesign.com`, live via Vercel's auto-deploy from this repo's `main` branch. Check whether any em dash here is inside a **user-visible string** (for example, a form success/error message, or ticker catchphrase text) versus a code comment. If it's user-visible, fixing it here and pushing to `main` will change what visitors actually see, flag this clearly so Sobhy knows a push to this repo (separate from the WordPress-side push above) will make it live.
- **`wp-custom-edits\HTML\footer-social-icons\README.md`** and **`wp-custom-edits\Docs\wp-reference.md`** are internal reference docs only, not pasted anywhere live, treat these the same as the rest of `docs/`.
